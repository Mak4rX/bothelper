# Калькулятор решти — дизайн

Дата: 2026-07-26
Статус: затверджено користувачем, готово до плану реалізації

## Контекст

BotHelper — облік каси кіберклубу. Веб-інтерфейс (`webapp/main.py` + `webapp/static/index.html`)
задеплоєний на Railway і є єдиною частиною, що реально працює в проді;
Telegram-бот (`bot.py`) у контейнері не запускається.

Інтерфейс має три головні вкладки:

| Вкладка | Де живе логіка |
|---|---|
| 💼 Управління касою | бекенд, `/api/reports`, `/api/collections` |
| 🧮 Калькулятор годин | бекенд, `/api/calculator/*` (`pricing.py`) |
| 💵 Рахунок каси | цілком у браузері, функція `calcCash()` |

## Мета

Касир називає клієнту суму, отримує готівку і має швидко порахувати решту.
Зараз це рахується в голові. Треба: ввести суму замовлення виразом
(`50+100`, `3*70`), ввести скільки дали готівкою — і одразу побачити решту
та якими купюрами її видати.

## Не входить у задачу

- Збереження історії розрахунків (окремої таблиці в БД не буде).
- Прив'язка до звітів, інкасацій і статистики.
- Дублювання логіки в Telegram-боті.
- Виправлення інфраструктурних проблем (volume, `DB_PATH`, авторизація) —
  вони зафіксовані окремо і свідомо відкладені користувачем.

## Рішення

Розрахунок цілком у браузері. Причини:

- Касир рахує при клієнті — мережевий round-trip на кожне натискання
  клавіші неприйнятний.
- Вкладка «Рахунок каси» вже так влаштована — узгоджуємось із наявним кодом.
- Бекенд не змінюється взагалі.

Відкинуто: варіант з ендпоінтом на Python (виграш — переюз у боті, але бот
у проді не працює) і гібрид (дві реалізації однієї формули розійдуться).

## Інтерфейс

Четверта головна вкладка `💱 Решта` поряд із наявними трьома.

Два текстові поля, обидва приймають арифметичний вираз:

1. **До сплати** — `50+100`, `3*70`, `2*80+50`, дужки.
   Під полем живий підсумок `= 150 ₴`.
2. **Дали готівкою** — теж вираз (клієнт дав 200+50).
   Під полем живий підсумок `= 250 ₴`.

Результат перераховується на кожен `input`, без кнопки.

| Ситуація | Що показуємо |
|---|---|
| Дали більше | плашка `Решта: 100 ₴` + розбивка `100₴ × 1` |
| Дали менше | червона плашка `Не вистачає 30 ₴`, розбивки немає |
| Рівно | `Без решти ✅` |
| Порожнє поле | результат прихований, помилки немає |
| Хибний вираз | поле підсвічене червоним, результат прихований |

Кнопка `🗑 Очистити` скидає обидва поля — як у «Рахунок каси».

Стилі беремо наявні: `.panel`, `.form-group`, `.btn`, `.btn-secondary`,
`.cashcount-total-box` / `.cashcount-total-label` / `.cashcount-total-amount`
для плашки результату, `.denom-badge` для номіналів у розбивці.

## Граматика виразу

Рекурсивний спуск, **без `eval()`** — застосунок публічно відкритий,
`eval` на користувацькому вводі неприйнятний.

```
expr    := term (('+' | '-') term)*
term    := factor (('*' | '×' | '/' | '÷') factor)*
factor  := ('-' | '+')* primary
primary := number | '(' expr ')'
number  := digits [('.' | ',') digits]
```

- Пробіли ігноруються цілком: `8 680` → `8680`.
- Кома — десятковий роздільник: `50,5` → `50.5`. Роздільника тисяч у виразі
  немає (усередині арифметики він не має сенсу).
  Це свідомо розходиться з `parse_amount()` у `bot.py`, де кома
  відкидається; бота ця зміна не торкається.
- Порожній ввід (або самі пробіли) — не помилка, а «нічого не введено»:
  `parseExpression` повертає `null`.
- Знак після бінарного оператора допускається — `50++100` це `50 + (+100)`
  = 150, `50--100` це `50 - (-100)` = 150. Забороняти немає сенсу,
  граматика `('-' | '+')* primary` це вже покриває.
- Будь-який інший символ, незакрита дужка, два бінарні оператори поспіль
  (`50+*100`), оператор без операнда — помилка.

## Числова модель

Усі обчислення — **цілі копійки**, ніякого float: `0.1 + 0.2` у float дає
`0.30000000000000004`, а це каса.

- Літерал числа розбирається як рядок: ціла частина × 100 + дробова,
  доповнена/обрізана до двох знаків. Точно, без похибки.
- `+`, `-` — цілі операції над копійками.
- `*` — `round(a * b / 100)`, бо копійки × копійки дає копійки².
  `3*70` → `300 * 7000 / 100 = 21000` коп = `210 ₴`.
- `/` — `round(a * 100 / b)`. Ділення на нуль — помилка.
- Округлення на кожній операції, не наприкінці — передбачувано і просто.
- Діапазон реальних сум (< 10 000 ₴) далеко в межах `Number.MAX_SAFE_INTEGER`.

## Розбивка решти

Номінали в копійках, від більшого:

```
100000  50000  20000  10000  5000  2000  1000  500  200  100   ← 1000₴ … 1₴
    50     10                                                   ← 50 к, 10 к
```

Жадібний алгоритм: для кожного номіналу беремо `floor(залишок / номінал)`
штук. Для канонічного набору гривні жадібний вибір дає мінімальну кількість
купюр.

**Заокруглення до 10 копійок.** З 2019 року готівкові розрахунки в Україні
заокруглюються до найближчих 10 копійок — монет 1 і 5 копійок в обігу немає.
Тому решта заокруглюється до 10 к, і якщо заокруглення відбулося,
показуємо приписку `заокруглено до 10 к`. Без цього правила розбивка
видавала б «0,03 ₴», яких фізично не існує.

## Файли

| Файл | Зміна |
|---|---|
| `webapp/static/change.js` | новий: чисті функції `parseExpression`, `makeChange`, `formatUah` |
| `webapp/static/index.html` | кнопка вкладки, панель `#change`, обвязка подій |
| `tests/change.test.mjs` | новий: тести парсера і розбивки |

Логіка виноситься в окремий модуль, а не інлайном у `index.html` (уже 62 КБ):
парсер арифметики і жадібна розбивка — саме той код, який треба покрити
тестами, а інлайн-скрипт усередині HTML тестами не покриєш.

`change.js` — ESM з іменованими експортами; наприкінці файлу
`if (typeof window !== 'undefined') window.ChangeCalc = { ... }`, щоб
інлайнові `oninput=` / `onclick=` обробники в `index.html` (наявний стиль
коду) бачили функції. Підключення — `<script type="module" src="/static/change.js">`.

## Контракти модуля

```js
// Повертає ціле число копійок, `null` для порожнього вводу,
// або кидає ParseError із полем .position
parseExpression(input: string): number | null

// change: копійки решти (> 0)
// Повертає { rounded: number, wasRounded: boolean,
//            breakdown: Array<{ denom: number, count: number }> }
makeChange(change: number): ChangeResult

// 21000 → "210 ₴", 5050 → "50,50 ₴"
formatUah(kopiykas: number): string
```

`index.html` відповідає лише за DOM: читає поля, ловить `ParseError`,
малює результат. Арифметики в ньому немає.

## Тести

`node --test tests/` (Node v22 у наявності).

Парсер:
- `50+100` → 15000; `3*70` → 21000; `2*80+50` → 21000
- `(50+100)*2` → 30000; пріоритет: `2+3*4` → 1400
- унарний мінус: `-50+100` → 5000
- пробіли: `8 680` → 868000
- кома: `50,5` → 5050; крапка: `50.5` → 5050
- `×` і `÷` як синоніми `*` і `/`
- знак після оператора: `50++100` → 15000, `50--100` → 15000
- помилки: `50+`, `(50`, `50)`, `5/0`, `abc`, `50+*100`, `()`
- порожній рядок і самі пробіли → `null`, не виняток

Розбивка:
- 100 ₴ → `100₴ × 1`
- 137 ₴ → `100₴ × 1`, `20₴ × 1`, `10₴ × 1`, `5₴ × 1`, `2₴ × 1`
- 0,50 ₴ → `50к × 1`
- 3 копійки → заокруглено до 0, `wasRounded: true`
- 7 копійок → заокруглено до 10 к, `wasRounded: true`
- сума розбивки завжди дорівнює заокругленій решті (властивість)

## Ризики

- **Жадібний алгоритм.** Для набору гривні він оптимальний, але це
  твердження варто перевірити перебором на тесті-властивості, а не
  приймати на віру.
- **Заокруглення множення покроково** може розійтися з розрахунком
  «в один прохід» на довгих виразах. Для реальних чеків (два-три доданки)
  розбіжності немає; фіксуємо поведінку тестом.
- Файл `index.html` великий; правку робимо точковою, наявну розмітку
  не чіпаємо.
